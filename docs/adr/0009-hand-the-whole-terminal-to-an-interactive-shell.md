# Hand the whole terminal to an Interactive Shell

Virtui will give an Interactive Shell its real terminal rather than emulating one inside a panel. The application asks for the handover instead of performing it: invoking the shell Command records a pending Interactive Shell in `AppState`, carrying the Provider CLI process the Provider Workspace declared for that Resource, and the host — which owns the screen and the input reader — takes it, suspends, runs the process to completion, resumes, and reports the outcome back as an `AppEvent`. This is deliberately not a `ProviderRequest`: every other kind of provider work is dispatched to the background and completes through a channel, whereas a shell must own stdin, stdout, and stderr, and nothing may be drawn while it does.

Suspending stops the input reader before it gives up raw mode and the alternate screen, because a reader still polling the terminal would swallow the keystrokes meant for the shell; resuming re-enters raw mode and the alternate screen directly rather than constructing a second terminal, because building one installs a panic hook that wraps the previous one and a session with several shells in it would nest one hook per shell. Resuming does not depend on how the process ended, so a Provider CLI that never started, or one that exited badly, cannot leave the user without a terminal, and any failure is reported only once Virtui has a screen to report it on. Keys that arrived while the shell held the terminal are discarded on return: they were typed at the shell, not at Virtui.

Because a Resource carries the Interactive Shell its Provider offers, availability and the process implementing it cannot drift: a Resource its Provider declared no shell for has nothing to run, so the operation is absent rather than offered and refused. The handover blocks the event loop from the moment the pending shell is taken until its outcome is applied, which is why returning always refreshes the workspace the shell was opened in, and why the ordering — suspend, run, resume, refresh — can be verified against fakes of the terminal and the process without a real container, instance, or terminal.

Keeping a shell alive while the user navigates elsewhere in Virtui is a separate decision, not taken here.
