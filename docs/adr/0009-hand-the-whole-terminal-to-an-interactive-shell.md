# Hand the whole terminal to an Interactive Shell

Tuivir will give an Interactive Shell its real terminal rather than emulating one inside a panel. The application asks for the handover instead of performing it: invoking the shell Command records a pending Interactive Shell in `AppState`, carrying the Provider CLI process the Provider Workspace declared for that Resource, and the host — which owns the screen and the input reader — takes it, suspends, runs the process to completion, resumes, and reports the outcome back as an `AppEvent`. This is deliberately not a `ProviderRequest`: every other kind of provider work is dispatched to the background and completes through a channel, whereas a shell must own stdin, stdout, and stderr, and nothing may be drawn while it does.

Suspending stops the input reader before it gives up raw mode, because a reader still polling the terminal would swallow the keystrokes meant for the shell. What it does not give up is the alternate screen: the shell runs on it, wiped, rather than on the terminal Tuivir was launched from. Leaving it would uncover whatever the user had on screen before Tuivir started and open the shell in the middle of their own scrollback, and it would mean the shell's output, not their terminal, is what Tuivir hands back on the way out. Resuming re-enters raw mode and asks for the alternate screen again rather than constructing a second terminal, because building one installs a panic hook that wraps the previous one and a session with several shells in it would nest one hook per shell; asking for a screen never given up costs nothing and recovers the one case where it was, a full-screen program run inside the shell leaving the alternate screen on its way out. Resuming does not depend on how the process ended, so a Provider CLI that never started, or one that exited badly, cannot leave the user without a terminal, and any failure is reported only once Tuivir has a screen to report it on. Keys that arrived while the shell held the terminal are discarded before reading resumes, not after: they were typed at the shell rather than at Tuivir, and a reader started first is already competing for them, so a discard that followed it would leave whatever the reader had reached to act on Tuivir as commands the user never aimed at it.

Only a shell that never started is a failure Tuivir reports. A shell exits with the status of the last command typed into it, so a non-zero status is the user's own — a search that matched nothing, then Ctrl-D — and reporting it would put a modal in front of a user who did nothing wrong every time they left a shell on a failed command. Tuivir promised a shell and delivered one; what happened inside it is theirs. The application is told how the shell ended whether or not the screen came back, so a host whose terminal is beyond saving still carries that outcome out with it rather than losing it alongside the screen that would have shown it.

Because a Resource carries the Interactive Shell its Provider offers, availability and the process implementing it cannot drift: a Resource its Provider declared no shell for has nothing to run, so the operation is absent rather than offered and refused. The handover blocks the event loop from the moment the pending shell is taken until its outcome is applied, which is why returning always refreshes the workspace the shell was opened in, and why the ordering — suspend, run, resume, refresh — can be verified against fakes of the terminal and the process without a real container, instance, or terminal.

Keeping a shell alive while the user navigates elsewhere in Tuivir is a separate decision, not taken here.
