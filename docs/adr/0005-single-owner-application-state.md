# Keep application state single-owned

Tuivir's main event loop will exclusively own and mutate plain `AppState` — including the active `ProviderId` and the Resource Commands still running — together with the record of outstanding refresh requests. Provider work, terminal input, and timers publish results as events rather than sharing `AppState` through locks. Every background request has a unique `ProviderRequestId` and an explicit target containing at least its `ProviderId`, and a completion is accepted only while that request is still recorded as outstanding. Refresh requests and Resource Commands have deliberately different lifetimes: a refresh belongs to the Provider Workspace being viewed, so switching Provider Workspaces invalidates the previous one's refreshes and a late snapshot can no longer overwrite newer application state; a dispatched Resource Command instead stays attached to the Provider, Resource, and Command it was dispatched for until it completes, so navigating to another Resource or Provider Workspace never discards the Command or its outcome. Rendering reads the state without performing I/O. This keeps concurrency out of the domain state and allows navigation, refresh, Resource Command, and provider-switching behavior to be tested without a terminal or installed provider CLI.
